Section03Expert

What "hands-on Director" actually means in practice — five operating signals, each codified.

A Director who claims hands-on but cannot demonstrate it loses the interview at the technical screen. These are the signals the EAI panel will check.

SIGNAL 01
Reads code fluently
When a technical PR or notebook is presented, the Director can review it, suggest changes, ask the right questions. Not necessarily author it — but read it as a peer.
SIGNAL 02
Prototypes when it unlocks
When a stakeholder conversation is stuck, the Director can ship a working prototype within hours-to-days that moves the conversation. The Atlas concept is precisely this pattern.
SIGNAL 03
Diagnoses production issues
When a model misbehaves in production, the Director can sit with the engineer, read the dashboards, ask the data quality questions, narrow the failure mode.
SIGNAL 04
Knows the architecture trade-offs
RAG vs fine-tune · agentic vs deterministic · model card vs eval suite · latency vs cost · the Director can hold an architecture conversation at peer level.
SIGNAL 05
Calibrated on what to build vs buy vs delegate
The Director knows when their hands on the keyboard accelerate the team vs when it slows the team. This calibration is the seniority.
THE TEST
All five together · the floor
A Director who has 4/5 is hireable. A Director who has 5/5 is the one who scales the function. The candidacy must demonstrate all five concretely.
The interview risk is not that the Director claims "hands-on" — it is that the panel asks "show me." Bring the builder portfolio (Section 04). It IS the show.

Section02Foundations

GenAI architectures · five patterns to discuss fluently.

Each pattern has a use case sweet spot, a known failure mode, and a 2026-best-practice eval methodology.

PATTERN 01
Prompting + few-shot

Off-the-shelf model · domain prompts · few-shot examples.

Fastest to ship. Cheapest. Hardest to control behaviour at scale.

PATTERN 02 · DOMINANT
RAG (retrieval-augmented)

Vector DB + retrieval + LLM generation.

The pharma sweet spot — grounded responses, attribution, domain-current. Most AZ commercial use cases sit here.

PATTERN 03
Fine-tuning

Domain-specific model adaptation.

Stronger task fit · higher cost · governance demands (model card, eval, drift).

PATTERN 04
Agentic workflows

Multi-step reasoning · tool use · planning.

Highest potential, highest governance bar. Atlas multi-agent design directly applies here. The 2026 frontier.

PATTERN 05
Knowledge graphs + LLM

Structured knowledge + LLM reasoning.

Pharma biological knowledge graphs (BIKG-class) · GraphRAG · structured grounding.

PATTERN 06
Hybrid · classical ML + LLM

Deterministic classical ML for structured · LLM for unstructured.

Most production systems are hybrid. The Director's job is the boundary design.

The signal
A Director who can discuss these six patterns at peer level with engineering — when to choose each, what fails — passes the technical screen with confidence. The vocabulary IS the credential.

Section04Expert

Technical screen drill — eight questions at the level the heaviest gate will probe.

The technical screen is the differentiating round for this role. These eight go deeper than the traps: answer aloud at whiteboard pace, then compare against the model answer.

TECH 01
"Design a RAG system over our SOP and quality documents. Walk me through it."
Pipeline: document ingestion with version control → structure-aware chunking (SOPs have sections; respect them) → embeddings + hybrid retrieval (keyword + vector; pure vector underperforms on regulated terminology) → reranking stage → generation with enforced citations → grounding evaluation gate before any answer ships. The pharma layer: provenance to the exact SOP version is non-negotiable; stale-document detection; access control inherited from the source system; validation posture agreed with Quality up front (CSA mindset). Close: "I'd prototype retrieval quality first — it's where these systems actually fail."
TECH 02
"Your production model's acceptance rate dropped 20% in two weeks. Diagnose it."
Segment first: all users or a cohort? All task types or one? Gradual or step change? A step change points to a deployment event — upstream pipeline change, prompt/config change, UI change, model version bump. Gradual points to drift: data drift (input distribution moved) vs concept drift (the world changed). Then: read the dashboards in that order, check the change log, and do the Lean move — gemba: sit with three users and watch the model in their real workflow. Adoption drops are as often workflow friction as model degradation. Close: hypothesis → cheapest test → fix → add the missing monitor so it never surprises us again.
TECH 03
"Fine-tune or RAG for a pharmacovigilance triage assistant?"
Decompose the task. The knowledge component (current product labels, evolving regulations, case precedents) → RAG: auditable provenance, instant updates, no retraining cycle. The classification component (seriousness triage, fixed taxonomy, stable labels) → a fine-tuned or even classical supervised model can outperform and is cheaper per call. So: hybrid — RAG for knowledge, tuned classifier for routing, human-in-the-loop mandatory because PV is as high-stakes as it gets. The Director point: the framing "fine-tune OR RAG" is itself the trap; production systems compose.
TECH 04
"How do you evaluate an LLM workflow before letting it into production?"
Layers: golden dataset built with the business (not by engineering alone) → task-level metrics defined before building (accuracy, grounding rate, harmful-output rate, latency, cost per task) → LLM-as-judge for scale, calibrated against human raters on a sample → red-teaming for the failure modes that matter in this domain → acceptance thresholds agreed with the risk owner, in writing. Then it never stops: the eval suite becomes the regression test for every prompt, model, or pipeline change. Close: "no eval suite, no production — that's a standard-work rule, not a preference."
TECH 05
"Agentic or deterministic automation — how do you decide?"
Three axes: input variability (uniform → deterministic wins on cost and auditability; messy/unstructured → agentic earns its complexity) · error tolerance (regulated transactional steps → deterministic with full audit trail; research, triage, synthesis → agentic with HITL) · explainability requirement (if every decision must be reconstructable, deterministic core + generative assist at the edges). Pattern: most real enterprise processes end up hybrid — deterministic backbone, agentic handling of the unstructured edges. Close with an example mapped to one of the five candidate processes from Module III.
TECH 06
"What does 'production-ready' actually mean for an AI process change?"
Ten-item bar: SLOs defined · monitoring live (the six dashboard items) · rollback path tested · model card + decision log complete · named business owner and support model · data pipeline contracts versioned · security + privacy review closed · change management executed (training, comms, workflow redesign) · benefit-tracking baselined with Finance · technical debt register opened honestly. The point: "production-ready" is mostly organisational, not technical — which is exactly why a transformation Director owns it and not only an ML engineer.
TECH 07
"Walk me through how you'd review a data pipeline PR."
Reading order: the tests first (what does the author think can break?) → schema contracts and null/edge handling → idempotency (can it rerun safely after partial failure?) → secrets and credentials out of code → logging and lineage (can we trace a bad output back?) → cost (full scans? unbounded joins?) → then style, last. The Director posture: review as a peer, ask questions rather than dictate, and know when to approve-with-comments versus block. The goal of the review is the team's quality bar, not my fingerprints on the code.
TECH 08
"GenAI cost at scale is exploding. What are your levers?"
Seven levers, in rough ROI order: model routing (small model by default, escalate on complexity) · caching of repeated queries and intermediate results · context discipline (most token waste is prompt bloat) · batch processing for non-interactive workloads · distillation of stable, high-volume tasks into small tuned models · usage governance (who can call what, with budgets) · architecture review — sometimes the honest answer is that a step shouldn't use an LLM at all. Close: cost per task on the dashboard from day one, never discovered in the invoice.
